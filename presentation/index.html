02 / Pain Points 0:30 - 1:10

なぜ「脆弱性対応」はこんなにつらいのか？

🔍
1. 真偽確認の沼

公的機関だけでなく SNS (X等) の速報も巡回が必要。
「大げさなデマ」や「対策済み旧情報」の振り分けで消耗する。

🧩
2. コード特定の沼

複数システムで「どのファイルの何行目か」「実は未使用か」を調べる作業とテストが属人化する。

😰
3. 横展開＆報告の沼

直したあとも「別システムに漏れはないか？」と不安が残り、上司向けの報告資料作りが二度手間になる。

🎤 トーク原稿（0:30 - 1:10） 脆弱性対応で一番時間を奪われるのは、パッチを当てる作業そのものよりも「SNSの噂の真偽確認」「複数システムのどこで使われているか・未使用かの特定」「他システムへの横展開調査と上司への報告資料作成」という3つの沼です。
03 / Solution Pipeline 1:10 - 1:50

アイデアシート「8人の代理人」を4ステップに統合

Step 1: CHECK
🔎 真偽・深刻度精査

JPCERT / NVD / SNS情報を AI が照合し、確定・SNSデマ・対策済を即座に判定

① 情報収集する人
Step 2: APPLY / TEST
🛠️ 走査・パッチ・検証

社内4システムの行番号特定・未使用検出・パッチ適用＆unittestを自動実行

③ 構成収集 ⑤ パッチ ⑥ 未使用指摘 ⑦ テスト ⑧ 代替提案
Step 3: SUMMARY
💬 上司・同僚向け要約

非エンジニアにも伝わる「3行サマリー」と「全社横断マトリクス」を生成

④ 説明してくれる人
Step 4: OUTPUT
📊 3D ＆ 公式PDF

Three.js 3D マップ（Before/After切替）と白背景 A4 公式 PDF を出力

② レポート化する人
🎤 トーク原稿（1:10 - 1:50） アイデアシートで洗い出した「8人の代理人」を、旗印シートの4ステップ（CHECK → APPLY/TEST → SUMMARY → OUTPUT）に完全マッピングしました。
04 / Google Cloud Architecture 1:50 - 2:35

Google Cloud セキュアアーキテクチャ

🎤 トーク原稿（1:50 - 2:35） Google Cloud の構成です。Cloud Run は --no-allow-unauthenticated で保護し、外部からの未認証アクセスは IAM ゲートで 403 遮断します。バックエンドは実コード走査と unittest の結果を Gemini 3.8 Flash に渡し、JSON Schema で構造化出力します。
