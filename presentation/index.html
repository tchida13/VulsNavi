02 / Pain Points 0:30 - 1:10

なぜ「脆弱性対応」はこんなにつらいのか？

1. 真偽確認の沼

公的機関だけでなく SNS (X等) の速報も巡回が必要。
「大げさなデマ」や「対策済み旧情報」の振り分けで消耗する。

直したあとも「別システムに漏れはないか？」と不安が残り、上司向けの報告資料作りが二度手間になる。

07 / Antigravity Best Practices & Lessons 4:00 - 4:35

Antigravity 実践知見：20分放置で完走させた工夫と反省

1. /plan × /grill-me の徹底反復
Effort: High
  • 計画フェーズだけ Effort を High に集中投下
  • /grill-me で仕様の抜け漏れを潰し、完成した計画書を AGENTS.md に固定
  • 結果：実装フェーズはほぼ手放し（20〜30分放置）で完走
2. MainAgent 主導の軽量チーム連携
Multi-Agent
  • 大規模向けの /teamwork ではなく、MainAgent + エージェント間通信を採用
  • 実装・監査（jidoka-auditor）・プレゼン作成を並行稼働
  • UI更新完了時に別エージェントへ自動通知し、スクショ撮影〜Pages反映まで連携
3. 「作るAI」と「監査するAI」の分離
Jidoka 監査
  • 読取専用の監査サブエージェントとスキル（VulsNavi-pipeline）を定義
  • Gemini SDK 規約違反や Cloud Run 未認証公開を自動ブロック
4. 反省：UIデザインを計画に入れ忘れた
Lesson Learned
  • 初回出力でレイアウト崩れ・情報過多が発生
  • AIは最初のUI構造を引きずるため後からの修正が難航
  • 教訓：「1画面1ビュー」等のデザイン制約こそ /plan 段階で定義すべき
トーク原稿（4:00 - 4:35） Antigravityを使った開発の工夫と学びです。1つ目は、単純作業ではない /plan だけエフォートをHighにし、/grill-me と往復して計画書を徹底的に作り込んだことです。これで実装は20〜30分放置するだけで完走しました。2つ目は、/teamwork はOS改善など超大規模向けだとGemini 4 Argonに教わったため、MainAgentから複数エージェントへメッセージ通信させる軽量チーム構成にしたことです。一方、最大の学びは「計画段階でデザイン要件を入れ忘れたこと」です。最初に出てきたUIが崩れており、AIが初期実装の方針を引きずって修正に苦労したため、UI制約こそ最初の /plan に入れるべきだと痛感しました。
